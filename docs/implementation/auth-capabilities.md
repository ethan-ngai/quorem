# Authentication capabilities

Issue #55. Better Auth and `@better-auth/passkey` pinned to 1.7.7. Password mode remains explicit local-only; production credentials remain managed by Cognito. No automatic account linking by email.

`GET /api/auth/quorem-config` adds `passkey`, `providers` (configured Google, Apple, GitHub only), and `preferredOrigin` to `method`. Login canonicalizes same-port loopback aliases before submitting; other cross-origin redirects are rejected. Configure all auth/API/language JWT issuers consistently. Local WebAuthn requires `AUTH_ORIGIN=http://localhost:5180`; IP origins cannot be relying parties. Existing browser drafts remain scoped to their original browser origin. HTTPS production requires a DNS host; changing that host changes the passkey relying party.

Run auth migrations for `003_passkey.sql` before serving. The official plugin owns registration/authentication challenges and signature verification; RP ID derives from the exact configured origin. Enrollment requires a fresh authenticated session, never creates anonymous users. Management mutations explicitly require exact Origin, and the plugin scopes list/delete to the session owner. Public signup stays disabled in credential preview. JWTs remain in memory; HTTP-only session cookies remain the source of identity. `AUTH_PASSKEYS=false` disables routes/capability; passkey capability is automatically false on IP hosts.

Optional `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`, `APPLE_CLIENT_ID`/`APPLE_CLIENT_SECRET`, `GITHUB_CLIENT_ID`/`GITHUB_CLIENT_SECRET` enable their providers. Partial pairs fail startup. Apple secret is the provider-issued signed client-secret JWT, not a private key. Keep all secrets outside source control. Register callback `${AUTH_ORIGIN}/api/auth/callback/<provider>`. Missing credentials produce no active social sign-in controls; never simulate a successful provider flow. Direct social sign-in does not link matching existing emails. Current application still requires provider-verified email before protected API use; providers without verified email need an explicit future verification flow, not a bypass.

Tests: use a separate disposable `AUTH_TEST_DATABASE_URL`, never the development database. Protocol integration verifies session-required options, RP ID, invalid assertions, exact-Origin management, cross-user isolation, deletion, configured Google initiation, and absent provider rejection. Config tests cover capability defaults/disable and partial secrets. These do not prove browser/hardware registration/sign-in; acceptance still requires a real WebAuthn credential ceremony and provider callback using valid credentials. No Google/Apple/GitHub credentials were available during implementation.

Sources: [official passkey plugin](https://better-auth.com/docs/plugins/passkey), [social providers](https://better-auth.com/docs/concepts/oauth).

## Local account creation (#57)

`registration:true` is advertised only for local password mode with explicit loopback `SMTP_HOST`. New accounts use name, username, email and 12-128 character passwords. Better Auth hashes the password and creates an unverified user without a session. Its signed, one-hour verification link is sent over real SMTP; both username and email sign-in refuse unverified users and resend a link after correct-password entry. Verification returns to login, without automatic sign-in. Protected Go API access still requires a verified identity. No endpoint marks arbitrary emails verified.

`make dev` starts pinned Mailpit with its `mailer` Compose profile and configures local SMTP automatically. Standalone: `docker compose --profile mailer up -d --wait mailpit`, set `SMTP_HOST=127.0.0.1`, `SMTP_PORT=51025`, `SMTP_FROM=Quorem <accounts@quorem.local>`, restart auth. Local inbox: http://localhost:58025. Both SMTP and inbox bind only loopback; Mailpit retains at most 500 messages and sends nothing externally. Production password mode remains rejected; Cognito owns managed account creation/verification.

Signup and resend mutations require exact application Origin. Auth rate limits apply in local mode too: signup five attempts/minute, explicit resend three/minute, general auth thirty/minute per client. Mail adapter allows four concurrent sends with five-second connection/socket timeouts; overload fails rather than queuing indefinitely. Keep successful signup notices generic. Real-mail test sets disposable `AUTH_TEST_DATABASE_URL` plus `AUTH_TEST_MAILPIT_URL=http://127.0.0.1:58025`; it checks SMTP delivery, rejected off-origin signup, no session before verification, both credential sign-in gates, forged token rejection, verified database state and verified JWT after login.
