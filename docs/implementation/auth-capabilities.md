## Local account creation (#57)

`registration:true` is advertised only for local password mode with explicit loopback SMTP. Signup starts with email alone: `/api/auth/registration/start` sends a one-hour opaque link without creating a user or reserving a username. The login page exchanges its token via POST `/verify`, removes it from browser history, and receives a 15-minute HttpOnly, SameSite=Strict setup cookie. `/status` returns the verified email; `/complete` atomically consumes the grant and creates the verified user/credential using Better Auth's password hasher. Normal Better Auth sign-in then creates the session. Direct credential-first signup and legacy registration verification endpoints are blocked when this flow is enabled. Signed email-change confirmation/verification requests continue through Better Auth’s verifier.

Tokens/grants are stored only as SHA-256 digests. Origin checks, bounded JSON bodies, expiration, single-use row locks, uniqueness, and transaction rollback protect setup. Existing verified accounts are unchanged and directed to sign-in after email proof. Existing unverified accounts can replace abandoned credentials after proof; their prior sessions/passkeys/provider bindings are removed. Expired or used links offer a fresh email request. Username conflicts preserve the setup grant for retry.

`takeRateLimit` is a shared PostgreSQL-backed fixed-window primitive with scope/subject keys, atomic counters and server retry times. Subjects are hashed; state survives restarts and is shared across service instances. Mail uses a 60-second per-address cooldown, five sends per address per hour, and 100 sends total per hour. Registration POSTs additionally share a 60/minute request budget. Delivery failure rolls back send budgets/challenges, permitting immediate retry; request budgets remain consumed. `useCooldown` is the reusable UI countdown primitive; server enforcement remains authoritative. Request throttles use HTTP 429/Retry-After; mail throttles return the same generic response with retryAfter to avoid account disclosure. Fixed windows can permit bursts across a window boundary. Address limits alone do not establish sender reputation or replace production abuse monitoring.

`make dev` starts pinned Mailpit with its `mailer` Compose profile and configures local SMTP automatically. Standalone: `docker compose --profile mailer up -d --wait mailpit`, set `SMTP_HOST=127.0.0.1`, `SMTP_PORT=51025`, `SMTP_FROM=Quorem <accounts@quorem.local>`, restart auth. Local inbox: http://localhost:58025. Both SMTP and inbox bind only loopback; Mailpit persists its SQLite inbox in the `mailpit-data` volume and retains at most 500 messages and sends nothing externally. Production password mode remains rejected; Cognito owns managed account creation/verification.

Signup and resend mutations require exact application Origin. Auth rate limits apply in local mode too: signup five attempts/minute, explicit resend three/minute, general auth thirty/minute per client. Mail adapter allows four concurrent sends with five-second connection/socket timeouts; overload fails rather than queuing indefinitely. Keep successful signup notices generic. Real-mail test sets disposable `AUTH_TEST_DATABASE_URL` plus `AUTH_TEST_MAILPIT_URL=http://127.0.0.1:58025`; it checks SMTP delivery, rejected off-origin signup, no session before verification, both credential sign-in gates, forged token rejection, verified database state and verified JWT after login.

Registration validation is shared through `@quorem/contracts/auth` Zod schemas. Usernames contain 3–30 lowercase ASCII letters/digits; creation input normalizes case and removes other characters. Email editing allows ASCII email characters without spaces, with full Zod email validation before delivery. Passwords require 8–128 characters and at least one Unicode punctuation/symbol character; whitespace alone is not special. Optional name is trimmed, limited to 80 characters, and rejects controls. Omitted names stay empty in storage; presentation can fall back to username. Existing sign-in credentials remain usable.

## Profile management and recovery

Profile exposes optional name and mutable username through Better Auth `/update-user`, with shared Zod validation and exact-Origin checks. Immutable user IDs retain ownership when usernames change. Profile photos retain their dedicated storage route. Username rules appear below both signup and profile inputs.

`/change-email` uses Better Auth’s two-step email-change flow: confirm at the existing verified address, then verify the new address. Until both finish, the stored email is unchanged. Only signed email-change request types pass the registration verifier guard; Better Auth validates signature, expiry and account binding.

Password reset is available from Profile and Forgot password. Better Auth sends a one-hour link; the reset UI validates and confirms the new password, then `/reset-password` atomically consumes the token and revokes all user sessions. Shared password policy also applies to set/change-password endpoints. Public requests return generic responses for unknown accounts. Exact-Origin checks and persistent request/send budgets cover recovery and email changes; throttles return Retry-After and update the reusable UI countdown. Delivery failures and exhausted send budgets surface as errors, never a misleading success.

Account integration tests use disposable PostgreSQL and Mailpit: profile validation/ownership, both email-change confirmations, unchanged email before verification, reset policy/replay, old/new credential behavior and session revocation. Auth suites run serially because migrations and integration fixtures share the disposable schema.

The pinned Better Auth plugin context awaits delivery tasks and propagates their failures rather than swallowing them in the default background-task logger. Integration coverage verifies a repeated email-change confirmation returns an explicit 429/Retry-After without sending more mail.
