# Solution approaches

Ledger: [#513](https://github.com/ethan-ngai/quorem/issues/513).

Question content owns `canonicalApproachId` and up to eight ordered `approaches`. Each approach owns a stable ID, optional canonical title, default language, explanation, time complexity, auxiliary-space complexity and notes. Its `implementations` contain only `language` and `source`. No per-language metadata or overrides exist. Alternative approaches require names; an unnamed canonical approach displays as **Solution**.

The canonical approach must default to Python and contain nonempty Python code; SQL uses PostgreSQL. That same source is the future custom-input oracle and the default editorial. Additional approaches may default to any supported language. Submission runtime/starter registrations remain independent. Custom interviews retain explicit expected values with no authored approaches, and cannot bypass canonical-code validation for global publications.

`packages/questions` owns blank defaults, canonical code lookup, approach labels, approach/language selection and canonical promotion. Switching canonical approaches gives an unnamed predecessor the name Solution, preserving valid alternative naming. Draft normalization sorts code variants for stable import/seed comparisons; approach order remains meaningful. Publication validates unique IDs/languages, names for alternatives, canonical/default references, source bounds and supported runtimes. Unknown per-language metadata is rejected by the contract.

Admin selects an approach, edits its optional/required name and language code, then edits the shared explanation and complexity once. Authors may add approaches, add/remove non-default code variants, change an alternative's default language, or promote an approach containing Python code. The canonical approach must be replaced before removal. Canonical promotion never copies source. All editor variants use shared code, field, selection, tooltip and confirmation primitives.

Workspace guidance starts with the canonical approach and offers approach selection when multiple are available. Code prefers the workspace language, otherwise the selected approach's default language. Approach selection never changes the submission editor. Complexity selection is language-neutral and loads no code or explanation. Public metadata exposes only `hasSolutions` and `hasComplexity`. Existing active-match spoilers, interview hint gates, authorization and multi-stage editorial restrictions remain enforced.

PostgreSQL stores approach metadata in `problem_solution_approaches`; `problem_solutions` contains only approach/language/source keys. Registration rejects conflicting immutable replay. Shared projection functions serve authorized authoring and editorial reads; the complexity projection never queries code columns. Frozen judging cases, runtime identities and historical reference hashes are unchanged.

Migration 074 groups retained variants with identical explanations. Distinct explanations become separately named alternatives. Differing language complexity bounds and notes are folded into the group's shared notes, retaining their language labels. The canonical group has an optional blank title. Lossless drafts retain numeric lexemes and escaped NULs; revisions increment to reject stale saves and old import receipts clear. Migration helpers are removed after conversion. Repo fixtures and preparation/repair/import tools use the same new shape, with no runtime compatibility layer.

Frontend/backend require coordinated release through GitHub Actions because the prior schema is removed. Local validation uses disposable databases. Before completion, apply the local development migration and restart the actual local API, then verify the real editor through live Vite/HMR. Custom-input execution, compilation and output caching remain future work.
