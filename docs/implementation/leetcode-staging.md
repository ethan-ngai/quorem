# LeetCode source staging

Ledger: [#236](https://github.com/ethan-ngai/quorem/issues/236).

`python3 scripts/stage-leetcode.py /tmp/quorem-leetcode-stage` downloads pinned GitHub commit archives and writes `questions.json` and `report.json` to a new directory. The report records repository URLs, exact commits, counts, invalid or duplicate question identities, and unmatched company rows. Re-running with another output directory produces the same files for the same source archives. To update snapshots, change the commit pins after reviewing upstream changes and compare reports.

Each staged question retains the original source record, numeric public `frontend_id` as `leetcode_id`, and exact company directory names. Company `5. All.csv` rows join only by the LeetCode URL slug; duplicate associations collapse. Unmatched rows include questions absent from the free-question snapshot and must not be silently assigned by title. Company names are not merged by guesswork. Company associations are historical dataset tags, not verified interview claims. The source snapshots have different dates, so missing matches are expected.

This is **not** a Quorem question import or a database migration. It performs no database writes and cannot publish questions. The input lacks private tests and reference solutions, and source extraction can lose statement formatting or mistake SQL schemas for examples. Validate content, fixtures, and execution before any subsequent import or publication. Keep staging files outside the repository. Existing [question JSON import](question-import.md) requires a different, validated format.

`python3 scripts/prepare-leetcode-drafts.py /tmp/quorem-leetcode-stage /tmp/quorem-leetcode-drafts` joins a pinned [LeetCodeDataset](https://huggingface.co/datasets/newfacade/LeetCodeDataset) by slug and frontend ID, extracts annotated Python method signatures and literal named-argument cases without executing source, and produces incomplete question JSON drafts. It also saves matching [kamyu104 solutions](https://github.com/kamyu104/LeetCode-Solutions) as separate alternate references, without assuming they compile or agree. Source revisions and failures are in the report; draft problem metadata includes company associations and the LeetCode ID. Associations exceeding authoring limits fail structural validation rather than being silently truncated.

The upstream cases are publicly available and generated; they can include public examples and are not secret LeetCode tests. The converter puts up to 20 into draft `hiddenCases` for review, but does not establish correctness, compatibility with ordered comparison, or execution in Quorem. Examples intentionally remain empty, so publication fails until verified public examples and validated cases are supplied. No draft is claimed runnable solely because it converts. SQL and stateful problems are excluded by the Python signature extractor.

`python3 scripts/fetch-leetcode-public.py /tmp/quorem-leetcode-stage /tmp/quorem-leetcode-live --limit 10` caches public GraphQL metadata, HTML statements and snippets by numeric ID. It skips cached files, limits each invocation to at most 100 uncached requests, waits between requests, retries transient failures and verifies slug/ID. Paid-only content is discarded; no login or gated access is attempted. Fetch timestamps are recorded because live data is not a pinned snapshot. It does not obtain private tests or convert HTML to draft statements.

To compare references with extracted cases using the existing Python harness, run `docker run --rm --network none --read-only --cap-drop ALL --security-opt no-new-privileges --memory 512m --pids-limit 64 --cpus 1 --user 65534:65534 -v /tmp/quorem-leetcode-drafts:/drafts:ro -v "$PWD/scripts/validate-leetcode-drafts.py:/validate.py:ro" --entrypoint python quorem-python:local /validate.py /drafts --limit 30`. Output is JSON lines. Passing demonstrates agreement for those cases only; it does not prove the cases or ordered comparator correct. The sandbox must be used because source solutions are untrusted code.

For import candidates, the converter extracts public examples and selects 20 distinct typed corpus cases, excluding non-scalar results, unparseable examples and statements with likely ambiguous-output language. Candidates are in `candidates/`; rejection counts are in the report. Validate them with `python3 scripts/validate-leetcode-structure.py /tmp/quorem-leetcode-drafts/candidates > /tmp/structure.jsonl` and the container command above, replacing the mounted directory with `candidates` and removing `--limit` (optionally use `--jobs 8` and `--cpus 4`). Export matching, unchanged successes with `python3 scripts/export-leetcode-fixtures.py /tmp/quorem-leetcode-drafts/candidates /tmp/structure.jsonl /tmp/harness.jsonl /tmp/quorem-leetcode-fixtures --stage-report /tmp/quorem-leetcode-stage/report.json`. The generated manifest records source revisions, exported IDs and hashes. These files match the authoring import format and have passed the publication validator and the reference against every included case. The exporter does not write to a database or publish. Semantic ambiguity detection is conservative but incomplete, and passing the source reference does not prove generated expected results or copied statements correct. Review before publication.
