## Findings

1. **P1 — unbounded result limits in protected #559 edits.** `apps/api/src/application/list-query.ts:19` and `packages/contracts/src/pagination.ts:3` now accept any positive safe integer; baseline capped limit at 100. Consumers include `apps/api/src/modules/problems/queries.ts:45`, `apps/api/src/modules/problems/authoring/routes.ts:94`, and `apps/api/src/modules/interviews/lifecycle/routes.ts:88`; authoring `repository.ts:776` loads and validates every requested draft, and catalog `queries/repository.ts:142` projects full question payloads. Large requests can cause excessive DB/CPU/memory and timeouts. Coordinate with #559 owner: preserve arbitrary user-selected page sizes while establishing an explicit server-side resource bound or bounded transport strategy; do not silently restore a UX cap. Validate boundary/overflow tests, all three consumers, and large-request behavior. Protected files: do not modify in this sweep without coordination.

2. **P2 — readiness filtering validates the entire draft collection during each request.** `apps/api/src/adapters/postgres/problems/authoring/repository.ts:763` calls the publication validator per draft; `:789` loops through every matching draft with increasing OFFSET, within one transaction, to produce a page and exact total. Batching limits individual query size, not total work; large catalogs incur repeated validation and increasingly expensive scans. Canonical owner is question authoring/publication validation; consumers are dashboard draft lists and publish. Consider a persisted, revision-bound readiness projection maintained atomically whenever normalized draft content changes, derived by the same `preparePublication` authority (including runtime revision/config invalidation), so filtering/count/pagination become SQL operations. This requires a migration and explicit invalidation design; if runtime changes cannot be reliably versioned, retain current correctness and investigate keyset/bounded work separately. Test all draft creation/update/import paths, runtime changes, filtering/sort/count, concurrent edits, and disposable-PostgreSQL query/load behavior. Preserve current access predicates, lock behavior and error semantics.

3. **P2 — interview result rendering repeats authorization and database trips per case, and can repeatedly parse entire arrays.** `apps/api/src/adapters/postgres/judging/results/repository.ts:454` fetches one visible case at a time (`:483`); each case invokes separately authorized byte streams (`:360`, `:497`, `:514`). Fallback examples and hidden status arrays restart from the beginning and skip preceding elements for each ordinal (`:502`, `:523`), yielding quadratic parsing/reads for large arrays. Normal public results already use bounded byte windows (`:410`). Canonical owner is the result streaming adapter: batch visible case metadata and small case/result bytes under a fixed byte budget and preserve separate oversized streaming; consume legacy arrays once sequentially where visibility/ordinal semantics permit. Every window must revalidate identity, membership, epoch, row version and private-case visibility; no cross-window authorization caching. Validate interviewer/candidate visibility and revocation midstream, oversized/multibyte cases, mutation/version fencing, lossless output and scaling in Node and workerd with disposable PostgreSQL. Existing integration suite `results/integration.ts` is 1,506 lines and is the starting conformance owner, not a reason to duplicate stream implementations.

4. **P2 — catalog authorization predicate is copied across item and facet queries.** `apps/api/src/adapters/postgres/problems/queries/repository.ts:50` defines owner/library visibility, while `:150` and `:155` duplicate it for topic/company facets. A future visibility change can restrict results yet expose private metadata through facets, or yield inconsistent facets. Extract the precise owner/library predicate as an SQL fragment local to this query adapter and compose it in the three queries; retain current distinction that facets ignore other filters. Validate anonymous, global/private, own/other-owner and deleted/current-version cases in catalog Node and workerd tests. Do not merge authoring authorization: it has different admin/ownership semantics.

5. **P2 — authoring repository is an overloaded 1,001-line transaction owner.** `apps/api/src/adapters/postgres/problems/authoring/repository.ts:38` through `:1001` mixes author/grant authorization, filtering/facets, draft commands, import batching, publication/deletion and operator-only seed repair. It obscures lock ordering and makes the publication validator and authorization harder to inspect. Existing `authoring/mutation.ts` and `../publication.ts` already own focused operations. Move cohesive list/query and import operations into adjacent modules, leaving a small repository composition with shared typed transaction/authorization primitives; preserve single-transaction scope, savepoints, lock order and all consumers. This is decomposition, not a new generic repository framework. Verify existing authoring integration/worker tests and batch failure/authorization cases on disposable PostgreSQL. Avoid touching protected `repository.test.ts` while #559 owns it.

6. **P3 — capability rule has two implementations with different locking needs.** `apps/api/src/adapters/postgres/access/repository.ts:26`–`:52` evaluates account status, active grants, internal override and admin; `problems/authoring/repository.ts:136`–`:155` independently evaluates the same `questions.custom` rule and adds `FOR SHARE` for mutations. Drift can make advertised capability disagree with actual authorization. Extract a narrowly scoped PostgreSQL authorization primitive for active grant/account policy with explicit read versus locking mode; avoid calling the current broad capability reader (it adds quota reads and lacks locking). Preserve 403 versus missing-user behavior, admin/global distinction, and locks; test revoked/expired/future grants, disabled/guest/admin and concurrent revocation. Defer if locking contract cannot be preserved cleanly.

- Authoring module decomposition (#5), owner `problems/authoring/` excluding protected test; coordinate with #2/#6 because they share files. #2 needs design and migration before implementation, not a superficial split.
- Result stream windowing (#3), owned by `judging/results/`, independent of authoring, with security-focused integration validation.
- #1 belongs to the active #559 owner; #6 follows authoring decomposition or remains separate only after clear ownership.

No dependency replacement recommended from manifest inspection alone; maintained-package suitability, provider compatibility and behavior require targeted investigation. No migration/backfill deletion is justified by filename: retained operator recovery and checksum history require deployment evidence.

## Implementation disposition — backend slice

Catalog item and facet queries now compose one owner/library visibility predicate; disposable-PostgreSQL tests cover anonymous, owner, other owner, global/private and private facets. Authoring list filtering, facets and pagination now live in a focused query module; transaction and authorization remain caller-owned. The authoring repository falls from 1,001 to 840 lines. Import remains with its closely coupled draft/publication helpers; an injected dependency bundle would add indirection without deleting complexity.

Readiness still validates the entire matching collection for exact totals, but now advances batches by SQL keyset with the sort key resolved in PostgreSQL, preserving timestamp microseconds. A 105-draft fixture checks all sort modes and directions, ties, both readiness states and multiple batches. Persisted readiness and validator/runtime invalidation remain unresolved. Capability-lock consolidation is tracked in #568. No schema change included. Catalog and authoring Node/workerd suites passed against separate disposable PostgreSQL containers; authoring Node suite skipped its separate canonical-migration fixture without its database URL. API typecheck and boundary check run in this branch; hosted and production validation not performed.
