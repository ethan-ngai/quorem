# 35c: Staged Hyperdrive and auth preflight

Issue #422. The staged Terraform module creates `cloudflare_hyperdrive_config.database` using the explicit PostgreSQL host, port, database, user, sensitive password and origin connection budget. It disables query caching and requires encrypted origin connections. The staged output `hyperdrive_id` now comes from this resource and remains the input to the generated `DB` binding. The database, credentials and stage network reachability are external inputs; no database is created by this module. The 5–100 connection budget must also fit the account plan and the database's other consumers. TLS `require` encrypts transport but does not establish hostname verification; configure and validate an authenticated origin policy for deployment.

Terraform marks the origin password sensitive, but sensitive values may still be stored in state and saved plans. Supply it through a protected environment/secret mechanism, require encrypted remote state and encrypted backups with tightly restricted access, and do not retain unencrypted plan files or print state. This module's existing S3-compatible backend deliberately does not provision or select the state store; its encryption and access policy must be verified before use. No real credentials, Terraform apply or cloud call were used here. [Cloudflare Hyperdrive Terraform reference](https://developers.cloudflare.com/api/terraform/resources/hyperdrive/)

Public stage configuration requires an explicit `AUTH_MODE` (`password` or `cognito`). Run `node scripts/hono-stage-preflight.mjs <public-input.json> <terraform-outputs.json>` with the applicable secret variables in the process environment. It validates the stage bindings and private credential separation, then constructs the real Worker auth runtime using the public variables plus supported secret names in memory. The stage requires `VERIFICATION_ACCESS_MODE=cloudflare-access` plus separate `VERIFICATION_ACCESS_CLIENT_ID` and `VERIFICATION_ACCESS_CLIENT_SECRET`; this depends on the 35d runtime contract and must not be deployed before that runtime is integrated. The DB and optional R2 bindings are local inert constructor inputs: this detects configuration/constructor errors, not database, provider, email or profile service reachability. Worker auth owns mode-specific checks, cloud email and mail key requirements, social provider pairs, SMTP rejection and profile processor checks. The CLI prints only a generic failure, never supplied secret values. The fixture selects explicit password login-only mode and is not a recommendation for production registration.

Validation: Terraform 1.13.5 / Cloudflare provider 5.28.1 schema, `fmt`, `validate` and mock-provider `test`; Node stage config, secret, Worker entrypoint and actual auth-constructor tests. Tests use fixture values only. No live-state migration or production route/class change is made. Hosted origin TLS identity, access policies, private service deployment and end-to-end provider behavior remain activation gates.
