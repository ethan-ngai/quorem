# 35e: First staged activation

Issue #427/#432. The isolated-stage workflow is `.github/workflows/hono-stage-deploy.yaml`; provisioning is authorized separately from production cutover. It runs only on `feat/hono-migration`. An explicit `deploy/hono/stage-request.json` commit containing `{"action":"stage","operation":"<uuid-v4>"}` triggers a fresh launch; ordinary code pushes do not provision. The declared manual action defaults to bootstrap plan only and requires the exact release SHA.

Validation precedes cloud work: lint/types/contracts, Node/workerd composition, trusted runner containers, deployment contracts and all three Terraform modules. The protected `hono-stage` job consumes the existing repository provider credentials and existing `NEON_PROJECT_ID`. Production resources, state keys and branches are excluded.

`hono-bootstrap` uses the existing Neon project. It creates an independent schema-only root branch, separate 0.25–1 CU/autosuspend compute, a new stage owner and empty `quorem_hono_stage` database. Production data is not copied, and the default branch is not changed. The project-scoped API key suffices; no new project or organization-scoped key is required. It retains the initial app/signing/runtime-password map in sensitive Terraform state; reruns never silently rotate it. Bootstrap, API and services use separate locked keys in the existing R2 backend. Before state access, the launcher checks that managed/custom public domains are disabled. R2 encrypts objects at rest; token access and state history must remain restricted. Saved plans use private temporary files and are removed; provider output and secret values are withheld.

The launcher publishes runner/verifier, five case images and the profile processor once, using the exact revision and actual registry digests. No placeholder digests enter a deployment. Only then does it call the fresh-stage owner with the already-published images. The database gate requires the dedicated name, direct verified TLS connection, migration permissions, no user objects and no peer sessions. It never resets a populated database.

Product/auth migrations precede a generation-specific non-owner runtime role and Hyperdrive. Queue consumption remains detached. The services Worker first exposes a non-authorizing zero namespace sentinel; signed discovery establishes the immutable namespace pin and canonical runner scope. New Custom Domains may retry transient namespace transport/DNS propagation for at most 120 seconds; invalid signatures and changed pins fail immediately.

Terraform owns service Custom Domains; Wrangler owns the API Custom Domain. This supports same-zone Worker fetches without duplicate domain ownership or dangling DNS records. Private endpoints authenticate distinct application bearer credentials; case and runner control observations remain signed and namespace-bound. Cloudflare Access is not provisioned or required. Both Workers must disable workers.dev and preview ingress.

After API deployment and scoped secret upload, signed case/runner controls activate. The workflow requires hosted case isolation/teardown proofs, a real manual-drain accepted submission, positive/negative application-authentication checks and profile image upload/read/delete. Queue attachment follows those gates; a second submission must complete automatically. The synthetic actor is revoked afterward; the receipt contains public release/namespace/proof metadata, never credentials.

Stage auth is explicitly login-only password mode. Hosted registration/reset/verification email is not configured or validated. Existing avatar migration, hosted browser/socket/load gates, maintenance/resume/update, retained-data backfills and production cutover remain separate gates.

Failure attempts queue detachment, control pause and a committed runtime-writer fence. State, jobs, checkpoints and uncertain resources remain intact. A populated or partially provisioned stage cannot be forced through the fresh launcher: inspect the recorded phase and use a reviewed recovery path; never reset data or roll back namespace history to make a retry pass. Successful local/mock validation does not establish hosted success; record the actual workflow receipt separately.
