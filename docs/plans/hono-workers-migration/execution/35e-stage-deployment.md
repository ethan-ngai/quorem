# 35e: First staged activation

Issue #427. `.github/workflows/hono-stage-deploy.yaml` is manual with `plan` default. Both actions require the exact workflow SHA on `feat/hono-migration`; stage uses the protected `hono-stage` environment. Validation runs the Node/workerd composition suite, container runner proof, Terraform tests and focused deployment tests before either action. The two Terraform stacks use separate locked keys in an existing encrypted, access-restricted R2 backend. Provider output is withheld; plans expose only constrained resource names/actions and counts. The workflow retains no saved plan or separate secret artifact. Cloudflare provider 5.28.1 marks [Worker binding text](https://raw.githubusercontent.com/cloudflare/terraform-provider-cloudflare/v5.28.1/internal/services/worker_version/schema.go) and [Hyperdrive origin passwords](https://raw.githubusercontent.com/cloudflare/terraform-provider-cloudflare/v5.28.1/internal/services/hyperdrive_config/schema.go) sensitive but not write-only: both persist in Terraform state and may persist in saved plans. Encrypted state and backups, restricted access, retention controls and credential rotation are prerequisites; redacted output does not prove these controls.

The stage action is limited to first activation of an empty, dedicated `quorem_hono_stage` database. Before cloud mutation it checks exact database name and configured host/port, `sslmode=verify-full`, migration-role privileges, absence of existing user-schema relations and peer sessions. The session snapshot is supplementary, not proof of an old-writer drain. The action never clears or recreates the database. Existing-data updates, legacy backfills and production cutover require the separate #38 maintenance/drain contract.

After the fresh check and locked namespace plan, the action provisions Hyperdrive with queue consumption disabled, migrates product and auth schemas, then builds the runner/verifier and five case images from the checked-out revision, pushes SHA tags and obtains matching repository digests. It provisions staged private services with queue consumption disabled. For a new service namespace, it deploys a non-authorizing zero sentinel, obtains a signed namespace, and creates the immutable Terraform state pin. Existing pins require a matching signed namespace before updating services. The API runner peer scope comes from the canonical remote sandbox owner. It validates the actual Worker auth constructor, deploys the API and uploads only the validated API secret projection through Wrangler stdin; private signing keys and host-only credentials are excluded.

The action runs the 36d signed hosted case/teardown matrix, then creates a short-lived synthetic actor with the 37i fixture. It exchanges that session for the normal Bearer token, creates a workspace and requires a real accepted submission through the deployed Worker and private manual drain. Valid-bearer Access controls must then succeed while the same private requests without Access credentials fail. Only then does it attach the queue consumer and require a second accepted submission without a manual drain. A failed or uncertain queue attachment/proof triggers a detach attempt; unconfirmed detachment requires operator intervention. The actor session is revoked in `finally`; submissions and uncertain jobs are preserved.

Namespace pin validation used real local Terraform data state: zero→A and A→A passed; A→B, A→zero, destroy and rollback failed. The fresh gate passed against an isolated TLS PostgreSQL database and rejected an existing auth table. Focused deployment tests use fake provider/network adapters and do not constitute hosted proof. No workflow, live plan, apply, migration, image push or deployment was invoked here. The private services migration-history fix is included and locally mock-tested; repeated hosted updates remain unverified. Do not invoke stage until the #38 recovery/update contract is reviewed. Actual hosted TLS/ingress, full execution, queue delivery and provider behavior remain unverified.

If activation stops after migrations or partial provisioning, leave the queue detached, preserve all state and jobs, inspect the migration ledgers and staged resources, and use the separately reviewed maintenance/resume contract. The fresh-only action intentionally refuses to rerun on a populated database; do not reset it or blindly roll back schema/state to force a retry.

The action queries Cloudflare for both Workers’ `workers.dev` and preview settings and requires both disabled before hosted acceptance ([Cloudflare API](https://developers.cloudflare.com/api/resources/workers/subresources/scripts/subresources/subdomain/)). The expected zone routes and Access policies still need hosted validation; this does not prove absence of out-of-band routes in unrelated zones. Credentials are scoped to the plan or activation step, not dependency-install steps.

Optional profile media provisions a distinct staged R2 bucket and image service, binds the exact Terraform bucket output, requires a separate Access pair and matching image bearer, and builds the image from the release revision. Before queue attachment, the staged probe uploads, reads and deletes a synthetic profile image and checks image-service Access denial. Existing profile object migration remains a separate cutover gate.
