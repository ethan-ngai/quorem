# 12c: shared profile mutation admission

Node profile photo mutations use PostgreSQL admission shared across handler instances. An advisory transaction lock serializes a 60-second, ten-attempt per-subject window, at most 10,000 live subjects, and four global active leases. Lease IDs, subject hashes, and generation tokens fence idempotent release. Window expiration is evaluated after acquiring the lock. No network or image processing occurs within a database transaction. Node uses the shared connection lifecycle and qualified Drizzle profile repository; uploads remain unmounted in the Worker.

A request deadline and disconnect signal stop subsequent stages and cancel a pending request-body reader. Already-started image processing, storage, database work, and cleanup must settle before release; no Promise race or deadline alone reclaims a lease. Sharp and the storage adapters do not prove hard cancellation. A process crash, uncertain admission commit, or failed release can therefore strand capacity, deliberately failing closed. Automatic safe reclamation and liveness require a killable image execution boundary and verified termination/reconciliation in 12d; this slice does not provide them. An uncertain profile update retains the uploaded object to avoid deleting a possibly committed reference.

Validation on disposable local PostgreSQL 17 at port 55449: four admission tests passed (concurrent factories, bounded windows and subjects, expired leases, fenced/idempotent release, release failure, expiry after lock wait); fourteen profile tests passed including real Sharp and Better Auth session/revocation against PostgreSQL, plus abort during unfinished processing. Database migration/catalog parity passed on a second disposable database in the same container. Auth/database typechecks and direct Node imports passed. These tests do not establish hosted capacity, killability, or crash recovery. No cloud services or real mail were used.
