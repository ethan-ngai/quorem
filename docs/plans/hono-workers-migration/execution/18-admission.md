# 18: submission admission

`admissionRoutes` is an unmounted `/v1/submissions` transport. It authenticates before bounded UTF-8 parsing, rejects caller-supplied execution context, applies the existing source/custom-case limits, derives SHA-256 source identity and a Go-compatible command fingerprint, and requires both a durable execution recovery prearm and an awaited, two-second prewake before the admission transaction. Failed prewake admits no job. Unknown commit outcomes propagate without replay or a false rollback claim.

The workspace transaction locks the owner, checks the existing idempotency record, resolves immutable workspace, problem, language and revision server-side, locks a match and samples database time after the lock when applicable, validates the unlocked stage and custom cases with shared question rules, and holds owner/sponsor/global queue locks through admission. It writes submission, job, guest reservation, idempotency and execution dispatch intent atomically; match submit invokes the canonical 20a reconciliation owner in the same transaction. The response contains only id, state, source hash and admission time. NUL/numeric sidecars use shared PostgreSQL-safe storage and require the explicit lossless reader/writer capability gate. The tx-scoped `insertAdmittedExecution` is available to packet 26 only after that owner validates interview, document, source, epochs and question context; interview routes are not mounted here.

Migration 050 now distinguishes `deadline` and `execution` receipts. Each receipt operation filters its purpose; the execution recovery Durable Object drains/publishes committed execution intents before acknowledging its receipts. A prearmed retry alarm remains durable across lock timeout, delayed COMMIT and unknown acknowledgment, and generation fencing prevents a concurrent prearm from being erased. This revised 050 applies only to the unmerged disposable baseline; an already-applied database needs coordinated migration handling rather than editing history in place. Runtime composition must bind the execution-specific recovery actor and publisher before mounting this route.

Validation on disposable PostgreSQL 17 (port 55458): actual practice submit/run, concurrent idempotent retries, changed fingerprint conflict, one nonterminal owner, token/daily/global queue quotas, hidden cases, NUL gate, match deadline after lock wait, tx-scoped match reconciliation, and shared guest sponsor capacity passed. Native workerd/PG tests admitted and dispatched a job, and held an execution receipt lock over an early alarm to verify late-COMMIT recovery and cross-purpose isolation. Existing scheduling Node and workerd regressions passed against a rebuilt disposable 55453 database. The existing Go runner and `quorem-python:local` Docker harness executed a TypeScript-admitted submit and persisted `accepted`; a NUL custom-run fixture was also exercised with lossless reader/writer gates enabled. Go-derived canonical fingerprint vectors compare against actual `judging.Command` encoding. Hosted queue, Durable Object, Hyperdrive and judge deployment/capacity remain unverified; packet 26 owns interview admission and packet 36 owns deployment.

The complete database migration/catalog parity suite passed on a freshly migrated disposable database after the 049 constraint-name correction. A separate integration suite admits jobs through the Hono route, runs the existing Go judge and Docker harness, and reads results through the Hono results route. It covers accepted submission, queued and running cancellation with idempotent retries, cross-owner denial, and a private NUL fixture whose content remains hidden. The running-cancellation fixture waits for the actual sandbox; an earlier cancellation before sandbox creation produced teardown-unconfirmed and retained the owner slot as designed.
