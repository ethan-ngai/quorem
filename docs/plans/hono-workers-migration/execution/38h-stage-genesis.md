# 38h: Fresh-stage genesis

Issue [#432](https://github.com/ethan-ngai/quorem/issues/432). Migration 063 adds an operator-owned immutable singleton. `scripts/hono-stage-genesis.mjs` records the stable external database identity, namespace/scope, first signed genesis operation/release, first service bindings, owner-key digest and exact migration-062 checksum. Runtime grants exclude this table.

The bootstrap owner derives the database identity from Terraform's existing-project and new-branch outputs. First activation independently checks fresh resources/database, installs migrations and provisions a restricted runtime role. After signed runner preparation and CaseControl initialization, its awaited callback persists genesis before either authority activates. Failure invokes existing containment. The operator transaction takes the canonical recovery lock and table locks, verifies trigger ownership/enforcement and requires no current or inventoried attempts before first insertion. Identical retries preserve the original signed proof; changed bindings fail.

Recovery can verify the stored signature and bindings against a current signed case observation while runtime writers are fenced. This is a provenance primitive, not complete history or resume authorization: contiguous authorized generation history, known registration-before-forward policy, teardown, fresh credentials, acceptance and queue reattachment remain the resume owner's responsibility. Trusted privileged database/provider operators remain outside the runtime boundary. Missing genesis cannot be reconstructed from an empty inventory or silently backfilled for an existing stage.

`node scripts/hono-stage-validation.mjs` requires the self-contained PostgreSQL fixture and signed control callback tests. The fixture owns two sequential disposable databases, uses actual product/auth migrations and runtime grants, and checks preexisting history refusal, identical replay, changed identity/key, disabled guards, immutable records, denied runtime DML and fenced verification. The database catalog parity suite covers migration upgrade, repeat, fresh creation and restore. Hosted stages from revisions before this owner do not acquire genesis merely by deploying newer code.
