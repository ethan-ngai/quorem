# 36b: Container runner validation

Issue #417. Run `node scripts/hono-container-validation.mjs` from the repository root with Docker, workspace network access for image builds, and the `quorem-python:local` image (`docker build -t quorem-python:local -f apps/runner/Dockerfile .`). Missing Docker or image fails the command. It builds the actual staged runner and verifier images and a fixture image, creates an isolated disposable PostgreSQL container and shared volume, and removes its containers and volume. No development database, cloud or nested Docker daemon is used.

The canonical 36a admission test runs in a fixture container, with the runner and verifier images in its network namespace and the runner connected to the host daemon. They share one named volume at the same absolute fence path. The test admits a Python submission, executes it in a host-daemon sandbox, verifies the independent verifier's signed result, and reads `accepted`. It sends SIGTERM during a live sandbox and checks teardown and that the submission did not falsely complete. A second runner starts against the same fence volume while the first case is active; the submission stays running. A separate container checks an aged lock cannot be acquired and that its independently derived scope equals the first process's scope. This does not simulate abrupt host death or prove a remote-volume failover. The runner passes case input over stdin and uses sandbox tmpfs; it does not ask the daemon to bind a runner-container input path.

Local OrbStack run: the required end-to-end test passed; nonmatching suite tests were intentionally filtered. This is local evidence for the tested daemon and volume driver, not a hosted persistent-volume, failover, network isolation, or remote-daemon claim. Deployment must preserve daemon identity and shared fence inode/ownership, enforce private API and drain ingress, and validate the actual storage topology. Runner and verifier outbound Access credentials are `CLOUDFLARE_ACCESS_CLIENT_ID` and `CLOUDFLARE_ACCESS_CLIENT_SECRET`; the Worker drain uses separate `EXECUTION_DRAIN_ACCESS_MODE=cloudflare-access`, `EXECUTION_DRAIN_ACCESS_CLIENT_ID`, and `EXECUTION_DRAIN_ACCESS_CLIENT_SECRET` credentials. No hosted validation was performed.
