# 36a: Trusted Node runner runtime

Issue #413. Node entrypoints compose the existing private command client, checkpointed engine, Docker isolation, drainer and independent verifier. No database credentials enter the runner or sandbox. The verifier uses its own source credential and Ed25519 signing key; the API verifies its receipts. The runner and verifier each expose a separate private listener.

Start with `vp -C apps/runner run verifier` and `vp -C apps/runner run runner`. Configuration is mandatory before listening:

- Verifier: `QUOREM_VERIFIER_LISTEN`, `QUOREM_VERIFICATION_SOURCE_ORIGIN`, `QUOREM_VERIFICATION_SOURCE_KEY`, `QUOREM_VERIFICATION_SERVICE_KEY`, `QUOREM_VERIFICATION_SIGNING_KEY_FILE`. Keys are distinct 32-byte lowercase hex; the signing key is an absolute path to an Ed25519 PKCS8 PEM. Optional `QUOREM_VERIFICATION_TIMEOUT_MS` defaults to 30000.
- Runner: `QUOREM_RUNNER_MODE` (`http` or `continuous`), `QUOREM_RUNNER_LISTEN`, `QUOREM_RUNNER_COMMAND_ORIGIN`, `QUOREM_RUNNER_COMMAND_SECRET`, `QUOREM_RUNNER_DRAIN_SECRET`, `QUOREM_DOCKER_SOCKET`, `QUOREM_DOCKER_FENCE_ROOT`, `QUOREM_DOCKER_NAMESPACE`. Secrets are distinct, whitespace-free and at least 32 bytes. Optional `QUOREM_RUNNER_SLOTS` (1–8), `QUOREM_RUNNER_COMMAND_TIMEOUT_MS`, `QUOREM_SANDBOX_CLEANUP_MS`, and `QUOREM_RUNNER_RECOVERY_POLL_MS` have bounded defaults.

Origins require HTTPS, except loopback HTTP for local fixtures. Optional `CLOUDFLARE_ACCESS_CLIENT_ID` and `CLOUDFLARE_ACCESS_CLIENT_SECRET` must be supplied together and require an HTTPS origin; their headers are sent only to that pinned origin. Listeners are plain HTTP for a private host or TLS terminator; network isolation, authenticated TLS and hosting are deployment gates. The Docker socket is trusted. Its canonical, owner-only persistent fence directory must remain stable across restarts and shared wherever the daemon is shared. Startup prints the derived non-secret scope; configure that exact scope on the API credential. Never put credentials or fence storage in sandbox containers.

`GET /health` is liveness only. HTTP mode accepts authenticated `POST /internal/drain`; a 202 requires a durable continuation before wake acknowledgement. Continuous mode polls authoritative queue state and repairs missed wakeups; it does not acknowledge provider deliveries. Shutdown stops admission, aborts active work, and awaits the canonical teardown/fencing path. Failed or uncertain teardown retains its fence, fails subsequent drains and makes graceful shutdown exit nonzero; process death is not teardown proof.

Validation: the complete admission/runner suite passed 18/18; focused process, teardown and transport tests passed 9/9. Spawned Node verifier and runner processes exercised health, wrong-secret rejection, configuration failure and SIGTERM. Continuous mode performed real private queue polling with a local provider fixture. On disposable PostgreSQL 55686, an actual API admission passed through a separate Docker runner process, private API HTTP, separate verifier process and signed promotion to the authorized result. A second live Docker attempt received SIGTERM; the process awaited teardown, no matching container remained, and the submission was not falsely completed. Hosted networking, persistent-volume behavior, provider queues, hard resource isolation and crash recovery remain unverified.
