# 29a: immutable runner input foundation

Issue #402. Partial and unactivated: admission, private input transport, runner consumption, legacy backfill and cutover are not implemented. Existing full-fixture reads still apply.

Migration 053 adds content-addressed blobs verified by PostgreSQL SHA-256, concrete version and interview snapshot fixture indexes, and per-job input manifests. Fixture/job indexes are built unsealed, then sealed once; later reference changes fail. Job sealing checks its actual source digest, runtime/harness, concrete fixture, contiguous case count and sample count. Blob deletion is allowed only after all foreign-key references disappear; job/fixture retention controls referenced content. Source is a blob too, allowing paging instead of assuming legacy source size. Old writers and checkpoints must drain and existing fixtures require operator normalization before activation.

`indexRunnerFixture(tx, owner, raw)` is called within publication and admitted interview snapshot transactions. New bounded authoring payloads are parsed by the existing lossless codec, separated into metadata and stage/channel case blobs, inserted in batches and sealed. The 320-case PostgreSQL fixture verifies indexing and replay conflicts. Legacy normalization needs a separate streaming owner; passing a large legacy fixture through this function does not establish bounded Worker memory.

Admission integration uses `fixtureCaseRefs(tx, owner, channel, level)` to retrieve ordered fixed-size hashes, `storeCustomInput(tx, raw)` only after existing custom-case validation, then `bindJobInputs(tx, { jobId, owner, cases, caseCount, sampleCount, privateDetails, submitCasesAreSamples })` inside the existing transaction. The case selection and public/private channel assignment remain the admission policy owner's responsibility. Call after inserting the job and, for interviews, its `interview_execution` identity. Each `cases` entry is an ordered `{channel, hash}` obtained from the fixture index or validated custom input; samples use `sample`. The special interview sample fallback stores its cases only once, sets equal case/sample counts and `submitCasesAreSamples=true`. Sealing checks the resulting length and source/fixture/job binding; callers must still enforce correct selection and visibility.

Local checks: fresh disposable PostgreSQL migration and exact Drizzle catalog parity; 7 focused tests cover real publication and interview snapshot owners, 320 indexed cases, NUL preservation, conflicts, one-way sealing, source/fixture binding and cascading retention. These are not hosted capacity or a bounded-reader proof. The production migration is not deployed.

The private transport exposes a fixed-size manifest and 64 KiB pages for source, metadata and one case at a time. Each page rechecks the live job, attempt, sandbox scope, cancellation, runtime, limits and concrete source/suite identity. Node's private spool verifies a stable hash, size and channel across every page and checks the complete SHA-256 before making bytes readable to the execution owner. Temp files stay outside the sandbox and are removed on disposal or failure. Real workerd plus disposable PostgreSQL exercised 150 KiB metadata, page sizes and stale-attempt rejection; Node tests cover truncated, oversized, changed-hash and failed-lease reads. This transport is not yet consumed by the engine and does not alone prove streaming JSON comparison or per-case execution.

Migration 054 adds an epoch-checked active interview snapshot mapping and a claim fence. Private runner peers must be configured server-side with the literal `manifest-v1`; unsupported or absent protocol fails composition. The 27 claimant only selects sealed manifests and sets the matching transaction-local marker, while the database rejects an old Go-style attempt claim on any manifest job. Queue state and empty confirmation still count all pending jobs, so unbackfilled legacy work cannot be acknowledged as empty. The marker is a trusted service protocol guard, not a replacement for database role isolation. `setActiveRunnerFixture` requires the caller's locked question mutation and an already sealed snapshot; active question writer integration and existing-question backfill remain open, so this mapping is not yet an activation claim.

The Node sandbox input port now accepts a reopenable stream with declared byte size and SHA-256. Docker stdin uses backpressure and recomputes identity while writing; the remote adapter streams with the same signed digest. A real Docker fixture executes a streamed 2 MiB input and rejects a false digest; all five existing harnesses still pass. The existing Python harness reads at most 3 MiB, and a 4 MiB fixture was observed to truncate and fail JSON decoding. The existing remote service has its own 8 MiB request bound. These are existing provider/harness limits, not a newly imposed admission quota. The current engine still builds its request in memory; connecting paged inputs and streaming comparison remains open.

`createActiveRunnerFixture(tx, session, epoch, version)` is an unmounted producer for a question the canonical writer has already derived from a sealed version. It creates the snapshot and copies case hashes inside PostgreSQL, including the custom no-hidden fallback, then epoch-fences the active mapping. It does not send fixture bytes to the Worker. The caller must establish that the active question was derived from that version; it is not a legacy backfill verifier. The existing create/question writer still needs a bounded version-selection refactor and is not yet wired to this helper.

A shared streaming span reader now finds allowed top-level and nested case fields without retaining their values. The runner's case projection streams only args and per-call method/args; expected values remain in the trusted spool. A real Docker test executes a 180 KiB projected argument and checks neither top-level nor call expectations enter the sandbox request. This is a tested primitive, not the active engine path; streaming comparison, checkpoint provenance and normalized-admission integration remain open.

The manifest additionally carries the authoritative Odyssey level and a suite hash over the ordered channel and case-hash references. `inputCaseRef(job, ordinal)` obtains the hash, byte size and visibility without reading case contents. These fixed-size values support the forthcoming attempt-bound checkpoint provenance; the current checkpoint implementation still requires its existing full-spec representation.

Because normalized jobs deliberately leave legacy submission cases empty, runner composition now requires an explicitly selected engine advertising `manifest-v1`. The former whole-spec engine has no such capability and cannot be silently selected. There is currently no completed manifest-capable engine to activate.

Migration 055 prevents direct deletion of a job, version or snapshot input root while its domain parent exists; normal parent-retention cascades still remove it. Until normalized streaming result verification is complete, 27 explicitly rejects whole-spec loading and non-failure promotion for manifest jobs. A real PostgreSQL regression verifies that an empty fabricated accepted result cannot complete a normalized submission. The gate must be replaced by the actual streaming verifier before activation; cancellation and failure handling remain available.

Internal domain transactions may use `manifestCaseIdentity(tx, jobId, ordinal)` for sealed counts, channel, hash and size, and `manifestCasePage(tx, jobId, ordinal, offset)` for at most 64 KiB. These helpers do not themselves compare expected values or authorize a transition; the calling owner must hold its domain locks and use independently verified results.
