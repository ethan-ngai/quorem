# 12e: Private image transport

Issue #430. The existing isolated Sharp service accepts HTTP on a non-loopback interface only with `IMAGE_SERVICE_TRANSPORT=cloudflare-container`, `IMAGE_SERVICE_HOST=0.0.0.0`, an explicit port and a strong `IMAGE_SERVICE_TOKEN`. This is an explicit trust-boundary selection: the provider must supply private container routing, HTTPS and Cloudflare Access outside the container. Standalone mode continues to require TLS on non-loopback sockets. `GET /health` is bearer-authenticated and no-store. Image processing retains the child termination marker and uncertain-lease policy.

For nonlocal Worker media, set `PROFILE_MEDIA_ENABLED=true`, bind `PROFILE_BUCKET`, and provide the exact HTTPS `PROFILE_IMAGE_SERVICE_URL`, `PROFILE_IMAGE_SERVICE_TOKEN`, `PROFILE_IMAGE_ACCESS_MODE=cloudflare-access`, and distinct `PROFILE_IMAGE_ACCESS_CLIENT_ID`/`PROFILE_IMAGE_ACCESS_CLIENT_SECRET`. The shared execution transport pins the HTTPS origin, attaches Access credentials and rejects redirects. Local loopback fixtures may use mode `none`. The provider ingress must strip Access headers before forwarding to the service; Sharp children still receive an empty environment.

Local validation: 34 image/profile/Worker tests passed (one real-session profile test skipped without its separate auth DB), including actual non-loopback private transport, real Sharp, authenticated health, wrong bearer, standalone TLS, child termination, ambiguous outcome and Access origin/redirect handling. Native workerd with disposable PostgreSQL, local R2 and the private-container-mode image service passed real upload/read/delete, revocation and stale-CAS tests. Auth typecheck passed. Hosted private ingress, resource limits, R2 provisioning and existing-object migration remain deployment gates; no cloud calls were made.
