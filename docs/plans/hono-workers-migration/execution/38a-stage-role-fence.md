# 38a: Staged database writer fence

Issue [#432](https://github.com/ethan-ngai/quorem/issues/432). First activation provisions a separate migration operator and a per-release/generation runtime login through `scripts/hono-stage-database-role.mjs`. Hyperdrive receives the runtime credential only after effective privilege checks and a real connection succeed. Role names come from `deriveStageRole`; callers must not construct them independently.

The runtime receives product/auth DML, sequence access and schema usage. It cannot own objects, create schemas, inherit privileged roles, modify migration ledgers or mutate attempt inventory. Public and shared-group database CONNECT grants are revoked. Neon requires an unhashed password in SQL role DDL; the operator uses the TLS-verified connection and forces server-side SCRAM-SHA-256 storage. Statement logs and encrypted state remain restricted; operator diagnostics scrub credential values. See [Neon SQL role requirements](https://neon.com/docs/manage/roles).

`scripts/hono-stage-recovery-fence.mjs` takes the canonical nonblocking recovery advisory lock, commits NOLOGIN, terminates other client sessions and rechecks role attributes, ownership, memberships, prepared transactions, CONNECT-capable logins and remaining sessions. Failed verification leaves NOLOGIN in force. It never discards prepared work, resets data or automatically restores login. Previously switched-role sessions are included in termination. Trusted database/provider administrators remain outside the runtime fence.

The caller must use `quorem_hono_stage`, a distinct unswitched operator, and the canonical stage runtime role. The operator needs superuser, or CREATEROLE plus ADMIN OPTION over the runtime role and backend-signaling/statistics privileges. Prepared transactions, unexpected login authority, unsafe ownership or insufficient privileges prevent confirmation. Hosted provider privileges and Hyperdrive reconnection denial still require actual staging evidence.

Migration 062 records every newly assigned attempt, job and sandbox scope in the claim transaction. Missing scopes and scope changes fail. Inventory cannot be updated, deleted or truncated by runtime callers and has no cascading deletion or retention timer. Claims and cleanup use the canonical engine scope. Runtime privilege checks verify the inventory trigger, guard and ownership boundary.

The existing-stage [maintenance owner](38g-stage-maintenance.md) composes queue detachment, independently attempted signed runner/case pause, writer fencing, bounded PostgreSQL and signed CaseControl inventories, and canonical full-attempt teardown. Application bearer credentials and namespace/scope proofs protect private service ingress; staging currently uses no Cloudflare Access.

Maintenance proves containment and teardown of captured attempts. It does not prove complete historical coverage or authorize resume. Empty inventories and migration checksums cannot establish that older deployments retained every attempt. A resume owner must verify durable genesis-to-current history, provision fresh generation credentials, activate replayable signed controls, run acceptance and reattach the queue. Missing or untrusted history remains closed; see [38g](38g-stage-maintenance.md).

Local coverage includes disposable PostgreSQL role/fence/inventory tests, delegated administration, prepared work preservation, switched-role termination, real auth/product commands, and native workerd connection termination/reconnect denial. Run `node scripts/hono-stage-validation.mjs` with Terraform available; the owner creates separate disposable databases. This does not establish hosted behavior or production Go fencing.

References: [PostgreSQL role membership](https://www.postgresql.org/docs/17/role-membership.html), [backend termination privileges](https://www.postgresql.org/docs/17/functions-admin.html), [CREATE ROLE](https://www.postgresql.org/docs/17/sql-createrole.html).
