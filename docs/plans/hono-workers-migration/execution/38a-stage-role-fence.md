# 38a: staged database writer fence

Issue #432. `scripts/hono-stage-recovery-fence.mjs` provides a PostgreSQL role-fence primitive only; it is not wired to a workflow and is not a complete recovery or cutover. Its caller must first prove admission is quiesced, queue consumption detached, old runner credentials fenced, and every active sandbox attempt terminated with its canonical signed proof. PostgreSQL role changes do not prove those conditions.

The primitive accepts only a `quorem_stage_runtime_<12–32 lowercase hex>` role while connected to `quorem_hono_stage` as a distinct, unswitched operator. It rejects privileged runtime roles, inbound role memberships other than the explicit operator, prepared transactions, insufficient role-administration/signaling/statistics privileges, and any other login role with database CONNECT unless that role is an explicitly trusted superuser. PostgreSQL grants CONNECT to PUBLIC by default, so the stage database must have a restrictive CONNECT policy; this primitive does not silently modify it. Explicit trusted administrators remain able to bypass the fence and must be controlled independently. The operator needs superuser, or CREATEROLE plus ADMIN OPTION over the runtime role and `pg_signal_backend` / `pg_read_all_stats` privileges. Managed-provider availability is not yet established.

It takes a nonblocking stage advisory lock, commits `NOLOGIN`, terminates all other client sessions in the stage database (including previously switched-role sessions), and rechecks role, membership, prepared work, other CONNECT-capable roles and remaining sessions. If termination or verification fails, NOLOGIN remains in force: no automatic re-enable, transaction rollback, data reset or prepared-transaction discard. Concurrent privileged administrative role/grant changes are outside this advisory lock and must be fenced by the recovery control plane. Credential rotation, authoritative runner/case quiescence, per-release role provisioning and safe resume/update sequencing remain unfinished.

Local isolated PostgreSQL 17 at port 55598, database `quorem_hono_stage`, with `max_prepared_transactions=10`: `QUOREM_STAGE_RECOVERY_TEST_DATABASE_URL=<disposable-loopback-url> node --test scripts/hono-stage-recovery-fence.test.mjs` passed 7/7. It covered active/future login denial, transitive membership and PUBLIC CONNECT refusal, an already-switched session, delegated operator privileges, partial failure and prepared work preservation. With the same isolated DB, `node --test scripts/hono-stage-recovery-workerd.test.mjs` passed 1/1 using native workerd, the canonical request-scoped pg client and a local Hyperdrive-shaped binding: an active query failed after termination and a new request could not reconnect. This is not proof of Cloudflare-hosted Hyperdrive pool behavior, eventual reconnect denial or production Go fencing. No cloud state or live database was touched.

Sources: [PostgreSQL role membership](https://www.postgresql.org/docs/17/role-membership.html), [backend termination privileges](https://www.postgresql.org/docs/17/functions-admin.html).

The private runner ingress also exposes `POST /internal/pause`, protected by the existing drain Access policy, bearer and pinned namespace. It persists a one-way pause in the RunnerService Durable Object; later drains return 503 even after the object is recreated. A drain already admitted can remain in flight. This is not a teardown or inventory proof, and no recovery workflow calls it. Resume and release rotation require a separate audited contract; no generic unpause exists.

Local checks: `node --import ./deploy/test-register.mjs --test deploy/hono/services/worker.test.mjs` (7 passed) and `vp -C apps/api exec vitest run --config src/runtime/composition/vitest.services.config.ts` (3 passed). Existing history does not provide a complete inventory of all prior attempts: metering records guest attempts only, and receipts do not cover every claim. A claim-time durable inventory and its retention invariant are required before recovering a stage. Historic deployments without it require a separately proven cleanup gate.

Migration 062 adds a claim-time attempt inventory: an AFTER trigger records every newly assigned attempt, job and scope in the same transaction as the claim. Attempt IDs are unique, scope changes for an existing attempt fail, and updates, deletes and truncation of inventory fail. There is no cascading foreign key or retention timer. The security-definer trigger allows an ordinary claimant to record authority without direct inventory write access; trusted database owners remain able to change DDL and must be separately controlled. A scope/attempt index supports bounded keyset inspection. This migration does not backfill or certify any namespace: all historical coverage remains unknown, even with no current jobs or with terminal receipts. Fresh-stage coverage requires a separate proof that the namespace was activated under this invariant before its first claim. Recovery and cleanup remain unwired.

This focused trigger test does not replace full product migration/schema or actual claim integration checks.

Runtime DB roles must not own the table, functions or schema, disable triggers, or have DDL privileges; the recovery design must verify that ownership boundary.
