# 35d staged private services

Issue #424. This staged design gives the API/auth Worker separate private Cloudflare-hosted Node runner, Node verifier and CaseSandbox services. It does not alter the live Worker migration chain or provision any cloud resource. `infra/terraform/hono-services` owns a separate Worker, v1 Durable Object classes, three container applications, protected stage routes, DNS records and distinct Cloudflare Access policies. Worker subdomains and previews are disabled. Terraform state includes sensitive Worker binding values and must use an encrypted, access-controlled backend.

The private ingress accepts only HTTPS requests on three distinct staged origins: `POST /internal/drain` on the drain origin, `POST /internal/results/verify` on the verifier origin, and attested `POST`/`DELETE /internal/case/{attempt}` on the case origin. Each needs its own Access service token and bearer. It strips Access headers before forwarding; case ingress also strips the case bearer. Other hosts, paths and methods fail closed. `GET /internal/case/namespace`, protected by case Access and bearer, returns the actual namespace sentinel. A first staged provisioning can use a placeholder 64-hex sentinel to retrieve this value; drain stays unavailable until the configured sentinel matches. Set `case_namespace_id` to the returned value before enabling queue delivery. The existing case attestation implementation is shared with the old Worker; valid ordinal range now matches 058 rather than the old 320 limit.

The runner service receives only its command origin/secret, drain secret, case origin/secret, case namespace, case owner public key and its two scoped outbound Access pairs. It uses `QUOREM_SANDBOX_PROVIDER=remote`; no Docker socket or verifier signing key enters it. The verifier receives its source origin/secret, service secret, verifier signing private key and separate API Access pair. The case signing private key remains in the Worker. The trusted launcher writes only its own PEM under a private temporary directory with mode 0600 and removes it during graceful shutdown. Contestant containers remain the existing separate CaseSandbox, receive neither service credentials nor internet access, and are not nested Docker.

API-to-verifier transport requires `VERIFICATION_ACCESS_MODE=none|cloudflare-access`. The Access mode requires `VERIFICATION_ACCESS_CLIENT_ID` and `VERIFICATION_ACCESS_CLIENT_SECRET`, HTTPS and a secret distinct from runner, source, verifier and drain credentials. Configure stage as `cloudflare-access`; the queue-to-drain Access pair and the runner-to-case Access pair remain separate. `RUNNER_API_ACCESS_CLIENT_ID/SECRET` and `VERIFIER_API_ACCESS_CLIENT_ID/SECRET` are separate Worker secrets mapped only into their respective Node process. Terraform variables and the exact remaining secrets are declared in the new module; namespace and all keys must be provisioned independently.

Local validation: 39 existing router/case lifecycle Node tests, three scoped-ingress/container-lifecycle tests, three API config/transport tests, one native workerd signed case test with ordinal 400, one Worker queue test, and a Wrangler Worker dry-run passed. The new image built locally and booted a remote-mode runner and separate verifier; both health endpoints responded, unauthenticated requests failed and key files were 0600. Terraform 1.13.5 format/validate and three mocked plans passed. No cloud credentials or data were used.

Hosted Worker routes, Access enforcement, DNS, image rollouts, container isolation/teardown and end-to-end remote admission through signed promotion remain unverified activation gates. The 36c local CaseSandbox execution fixture can fail under workerd without cgroup privileges; the local image boot does not prove a hosted case execution. Production throughput, failure recovery and cross-host isolation require separate validation. Do not activate or deploy from this report.
