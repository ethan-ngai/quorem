# Identity service

Better Auth 1.7.7 owns sessions in `quorem_auth`. Default production `AUTH_MODE=cognito` delegates credentials, verification, reset and Google federation to Cognito. `AUTH_MODE=password` uses Better Auth username/password credentials, locally by default. Automatic account linking is disabled. Immutable Better Auth subjects map to internal users; matching emails never link identities.

Copy `.env.example` to `.env`, supply environment secrets, run `vp -C apps/auth run migrate`, then `make auth`. Container deployments can set `AUTH_HOST=0.0.0.0` (default loopback). Same-origin reverse proxy routes `/api/auth/*` to port 8082. Set API `QUOREM_DEV_IDENTITY=false`, `AUTH_ORIGIN`, `AUTH_SERVICE_URL=http://127.0.0.1:8082`, `AUTH_INTERNAL_SECRET`; set language `QUOREM_DEV_IDENTITY=false`, `AUTH_ORIGIN`, `API_IDENTITY_URL=http://127.0.0.1:8080`. Browser JWTs stay in memory, expire after five minutes. Go validates EdDSA, issuer, audience, expiry, verification and session identity, then checks live session and server-owned disable/role state. JWKS cache is bounded to five minutes with refresh throttling. Language authorization refreshes every 15 seconds. `/internal/*` is service-only, never proxy publicly.

Configure Cognito authorization code grant, `openid profile email`, callback `${AUTH_ORIGIN}/api/auth/callback/cognito`; register Google through Cognito. Managed login includes signup, verification, reset and federated sign in. Grant admin explicitly in product database `users.role`; never accept browser role flags. Logout clears the Better Auth application session; Go rejects it immediately. Cognito provider SSO may remain until Cognito logout is completed.

Local password mode requires `APP_ENV=local`, a loopback `AUTH_ORIGIN`, and no Cognito credentials. Run migrations, then `AUTH_SEED_PASSWORD=<12-128 characters> vp -C apps/auth run seed`. The script uses Better Auth signup and password hashing internally; public signup remains disabled unless loopback SMTP is explicitly configured; then account creation requires emailed verification before login. Seed usernames are `alice` and `bob`, with verified local fixture emails. Repeated seeds retain subjects and check the supplied password. Optional `DATABASE_URL` binds subjects to product users and grants Alice admin, Bob ordinary user; both seed databases must be loopback. Existing identities never link by email. Keep passwords and service secrets in ignored environment files.

`GET /api/auth/quorem-config` returns `{method: "password" | "cognito", passkey, providers, preferredOrigin}`; see [passkey and social support](../../docs/implementation/auth-capabilities.md). Credential login posts `{username,password}` to `/api/auth/sign-in/username`; JWT, profile and logout use the same authenticated service as Cognito. Outside local loopback, password mode requires `AUTH_PASSWORD_PRODUCTION=true`, HTTPS, and external email delivery. Seeding remains local-only. `make dev` now starts Mailpit and enables real local email verification; inbox http://localhost:58025. API public problem reads are anonymous. Run mock JWT/security tests with `go test ./apps/api/internal/identity ./apps/api/internal/httpapi`; auth config tests with `vp -C apps/auth test`. Set disposable `AUTH_TEST_DATABASE_URL` for real handler password/hash/session/logout and Cognito PKCE tests; optional disposable `PRODUCT_AUTH_TEST_DATABASE_URL` also checks immutable product bindings and seeded roles. Disposable database tests verify immutable mapping, roles and disable behavior. Real Cognito login/Google/verification/reset remains a cloud acceptance gate; configuration/unit tests do not prove those flows.

Sources: [Cognito](https://better-auth.com/docs/authentication/cognito), [JWT](https://better-auth.com/docs/plugins/jwt).

Profile photos consume the SDK-free `ProfileStorage` port in `profile-storage.ts`; provider construction lives in `infrastructure.ts` and `adapters/s3-profile-storage.ts`. AWS uses default IAM credentials, local Garage uses `AVATAR_S3_ENDPOINT`, region, bucket and explicit access keys in `.env.example`. Grant only GetObject/PutObject/DeleteObject under `avatars/`. The bucket stays private: public `GET /api/auth/profile-photos/<opaque UUID>` proxies only a currently referenced avatar, never arbitrary bucket paths. Revoked photo URLs return 404 (successful image responses cache for 60 seconds).

Authenticated `GET /api/auth/profile` returns `{name,email,username?,image?}`; `PUT /api/auth/profile-photo` accepts raw PNG/JPEG/WebP, max 5 MiB and 16 million pixels, and `DELETE` clears it. Mutations require a live session cookie and exact application Origin. Four simultaneous processors and ten mutations per user per minute bound work per service instance. Better Auth image updates are blocked at its user hook; provider photos cannot bypass storage or overwrite an uploaded avatar. Sharp decodes and re-encodes static images to at most 512px WebP, stripping metadata. Failed database writes discard uploads; replacement/deletion cleans the previous object. Cleanup failures log the opaque key for operational retry. No photo produces `image:null`; frontend renders name initials in HTML, with no generated image file.


## Provider boundaries

Select capabilities independently: `AVATAR_STORAGE_DRIVER=s3|r2` and `AUTH_EMAIL_DRIVER=smtp|ses-smtp|cloudflare`. Unset drivers retain existing local Garage/Mailpit configuration. PostgreSQL remains the only identity persistence implementation. No SDK types enter `ProfileStorage` or `EmailDelivery`; composition happens in `infrastructure.ts`. One verification sender serves account setup, email changes and password reset, retaining their existing PostgreSQL rate limits and a shared four-delivery concurrency budget.

S3 uses IAM credentials by default; Garage uses a custom local endpoint. R2 uses its account endpoint, region `auto`, and bucket-scoped S3 credentials. Both adapters implement private WebP put/get/delete only; reads stop after 5 MiB. Cloudflare does not require translating S3 IAM policies into R2 policies: provision each provider's credentials/permissions independently.

SES uses its official SMTP interface with separate SMTP credentials and mandatory TLS (465 implicit TLS; 587 STARTTLS). Generic external SMTP requires explicit selection and authenticated TLS. Cloudflare's outbound Email Service REST API is a beta capability, separate from inbound Email Routing, requiring an onboarded domain and entitled account. Its adapter checks recipient acceptance/bounces, times out requests and never retries an ambiguous send automatically. Provider acceptance does not guarantee inbox delivery. Delivery failures return generic errors; provider response bodies and credentials never reach account callers.

Production self-managed password authentication requires explicit `AUTH_PASSWORD_PRODUCTION=true`, HTTPS and an external email adapter; default Cognito mode remains supported. Seed creation still requires local loopback origin/databases. Configure each deployment's networking, secret delivery and mail sender domain separately. No cloud deployment or credential acceptance is implied by local adapter tests.

Primary references: [R2 S3 SDK configuration](https://developers.cloudflare.com/r2/examples/aws/aws-sdk-js-v3/), [SES SMTP](https://docs.aws.amazon.com/ses/latest/dg/send-using-smtp-programmatically.html), [Cloudflare outbound REST API](https://developers.cloudflare.com/email-service/api/send-emails/rest-api/).
